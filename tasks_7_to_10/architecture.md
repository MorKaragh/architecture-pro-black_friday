# Задание 7. Схемы коллекций и стратегии шардирования

## 1. Коллекция `orders` (Заказы)

### 1.1. Схема коллекции

```javascript
{
  _id: ObjectId,                    // Уникальный идентификатор заказа
  customer_id: String,              // Идентификатор клиента
  order_date: Date,                 // Дата и время оформления заказа
  items: [                          // Список заказанных товаров
    {
      product_id: ObjectId,         // Идентификатор товара
      name: String,                 // Название товара (для истории)
      price: Number,                // Цена на момент заказа
      quantity: Number              // Количество
    }
  ],
  status: String,                   // Текущий статус: "pending", "processing", "shipped", "delivered", "cancelled"
  status_history: [                 // История изменений статусов
    {
      status: String,               // Статус
      changed_at: Date,             // Дата и время установки статуса
      changed_by: String            // Опционально: кто установил статус (user_id, system, admin_id)
    }
  ],
  total_amount: Number,             // Общая сумма заказа
  geo_zone: String                  // Геозона заказа (например, "moscow", "ekaterinburg")
}
```

### 1.2. Основные операции

- **Быстрое создание заказов с одновременным списанием остатков**
- **Поиск истории заказов конкретного пользователя**
- **Отображение статуса заказа**

### 1.3. Индексы

```javascript
// Индекс для поиска заказов по клиенту (основной запрос)
db.orders.createIndex({ customer_id: 1, order_date: -1 })

// Индекс для поиска по статусу и геозоне
db.orders.createIndex({ status: 1, geo_zone: 1 })

// Индекс для поиска по дате (для аналитики)
db.orders.createIndex({ order_date: -1 })

// Индекс для поиска по истории статусов (для аналитики и аудита)
db.orders.createIndex({ "status_history.changed_at": -1 })
```

### 1.4. Стратегия шардирования

**Шард-ключ:** `{ customer_id: 1 }`

**Тип шардирования:** Range-based sharding

**Обоснование:**
- Все заказы одного клиента будут находиться на одном шарде, что обеспечивает:
  - **Локализацию запросов**: запросы по `customer_id` выполняются на одном шарде, это эффективно 
  - **Масштабируемость**: равномерное распределение нагрузки при большом количестве клиентов
- Геозона не используется как шард-ключ, так как это может привести к неравномерному распределению (некоторые города крупнее других)

Важно: если предполагается наличие клиентов, у которых уж очень много заказов, то чтобы не создавать горячих шардов стоит использовать ключ `{ customer_id: 1, _id: 1 }` - будет лучше.

### 1.5. Команды MongoDB для настройки шардирования

```javascript
// Включение шардирования для базы данных
sh.enableSharding("mobilny_mir")

// Создание индекса на шард-ключ (обязательно перед шардированием)
db.orders.createIndex({ customer_id: 1 })

// Настройка шардирования коллекции orders
sh.shardCollection("mobilny_mir.orders", { customer_id: 1 })

// Проверка статуса шардирования
sh.status()

// Проверка распределения данных по шардам
db.orders.getShardDistribution()
```

## 2. Коллекция `products` (Товары)

### 2.1. Схема коллекции

```javascript
{
  _id: ObjectId,                    // Уникальный идентификатор товара
  name: String,                     // Наименование товара
  category: String,                 // Категория товара (например, "electronics", "books", "accessories")
  price: Number,                    // Цена товара
  stock_by_geo_zone: [             // Остаток товара в каждой геозоне
    {
      geo_zone: String,            // Название геозоны (например, "moscow", "ekaterinburg")
      stock: Number                // Остаток товара в данной геозоне
    }
  ],
  attributes: {                     // Дополнительные атрибуты
    color: String,                  // Цвет (если применимо)
    size: String,                   // Размер (если применимо)
    // ... другие атрибуты в зависимости от категории
  },
  created_at: Date,                 // Дата создания записи
  updated_at: Date                  // Дата последнего обновления
}
```

### 2.2. Основные операции

- **Частые обновления остатков при покупках**
- **Поиск товаров по категориям и фильтрация по диапазону цен**
- **Описание товара на странице продукта**

### 2.3. Индексы

```javascript
// Индекс для поиска по категории и цене (основной запрос)
db.products.createIndex({ category: 1, price: 1 })

// Индекс для поиска по названию (текстовый поиск)
db.products.createIndex({ name: "text" })

// Индекс для поиска по категории
db.products.createIndex({ category: 1 })

// Индекс для поиска по цене
db.products.createIndex({ price: 1 })

// Для проверки остатков по геозоне (один индекс для всех геозон)
db.products.createIndex({ "stock_by_geo_zone.geo_zone": 1, "stock_by_geo_zone.stock": 1 })
```

### 2.4. Стратегия шардирования

**Шард-ключ:** `{ category: 1, _id: 1 }` 

**Тип шардирования:** Range-based sharding

**Обоснование:**
- Составной ключ `{ category: 1, _id: 1 }` обеспечивает:
  - **Локализацию запросов**: запросы по категории выполняются на ограниченном наборе шардов (но не гарантируется что все продукты категории будут ровно на одном шарде)
  - **Равномерное распределение**: `_id` как второй компонент обеспечивает равномерное распределение товаров внутри категории
  - **Масштабируемость**: при росте количества товаров в категории, они распределяются по шардам благодаря `_id`

Важно: Если некоторые категории значительно больше других, то стоит рассмотреть использование hashed sharding по id (ключ `{ _id: "hashed" }`)

### 2.5. Команды MongoDB для настройки шардирования

```javascript
// Включение шардирования для базы данных (если еще не включено)
sh.enableSharding("mobilny_mir")

// Создание индекса на шард-ключ (обязательно перед шардированием)
db.products.createIndex({ category: 1, _id: 1 })

// Настройка шардирования коллекции products
sh.shardCollection("mobilny_mir.products", { category: 1, _id: 1 })

// Проверка статуса шардирования
sh.status()

// Проверка распределения данных по шардам
db.products.getShardDistribution()
```

## 3. Коллекция `carts` (Корзины)

### 3.1. Схема коллекции

```javascript
{
  _id: ObjectId,                    // Уникальный идентификатор корзины
  user_id: String,                  // Идентификатор пользователя (null для гостей)
  session_id: String,               // Идентификатор сессии (для гостей)
  items: [                          // Список товаров в корзине
    {
      product_id: ObjectId,         // Идентификатор товара
      quantity: Number              // Количество
    }
  ],
  status: String,                   // Статус: "active", "ordered", "abandoned"
  created_at: Date,                 // Дата и время создания
  updated_at: Date,                 // Дата и время последнего обновления
  expires_at: Date                  // Время удаления (TTL) для автоматической очистки
}
```

### 3.2. Основные операции

- **Создание корзины**, когда заходит гость или новый пользователь
- **Получение текущей корзины** по фильтру `{ session_id, status:"active" }` или `{ user_id, status:"active" }`
- **Добавление или замена товара** в корзине
- **Удаление товара** из корзины
- **Слияние гостевой корзины в пользовательскую**, если пользователь залогинится:
  - прочитать гостевую `{ session_id, status:"active" }`
  - добавить её items в корзину `{ user_id, status:"active" }`
  - отметить гостевую как `abandoned`
- **Отметка корзины как заказанной**

### 3.3. Индексы

```javascript
// Индекс для поиска активной корзины пользователя (основной запрос)
db.carts.createIndex({ user_id: 1, status: 1 })

// Индекс для поиска активной гостевой корзины
db.carts.createIndex({ session_id: 1, status: 1 })

// Индекс для TTL (автоматическое удаление старых корзин)
db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })

// Составной индекс для операций слияния корзин
db.carts.createIndex({ user_id: 1, session_id: 1, status: 1 })
```

### 3.4. Стратегия шардирования

**Шард-ключ:** `{ user_id: 1, _id: 1 }` 

**Тип шардирования:** Range-based sharding

**Обоснование:**
- Составной ключ `{ user_id: 1, _id: 1 }` обеспечивает:
  - **Локализацию запросов**: корзины пользователей находятся на одном шарде
  - **Обработку гостевых корзин**: для гостей `user_id` будет `null`, но `_id` обеспечит распределение
  - **Эффективность операций**: все операции с корзиной пользователя выполняются на одном шарде
  - **Равномерное распределение**: `_id` как второй компонент обеспечивает равномерное распределение гостевых корзин
- Важно: при слиянии корзин (гостевая → пользовательская) обе корзины могут быть на разных шардах, но это редкая операция, и она выполняется один раз при логине

**Альтернативный подход для гостевых корзин:**
Если гостевых корзин очень много, можно использовать `{ session_id: 1, _id: 1 }` для гостевых корзин, но это усложнит логику. Рекомендуется использовать единый ключ `{ user_id: 1, _id: 1 }`, где для гостей `user_id = null`.

### 3.5. Команды MongoDB для настройки шардирования

```javascript
// Включение шардирования для базы данных (если еще не включено)
sh.enableSharding("mobilny_mir")

// Создание индекса на шард-ключ (обязательно перед шардированием)
db.carts.createIndex({ user_id: 1, _id: 1 })

// Настройка шардирования коллекции carts
sh.shardCollection("mobilny_mir.carts", { user_id: 1, _id: 1 })

// Проверка статуса шардирования
sh.status()

// Проверка распределения данных по шардам
db.carts.getShardDistribution()
```

# Задание 8. Стратегия мониторинга и реагирования на горячие шарды MongoDB

## 1. Обзор

Раздел описывает стратегию мониторинга, сбора метрик и реагирования на проблемы с горячими шардами в MongoDB.

### 1.1. Цели мониторинга

- **Проактивное выявление** дисбаланса нагрузки между шардами
- **Предотвращение** перегрузки отдельных шардов
- **Автоматическое реагирование** на критические ситуации
- **Анализ трендов** для планирования масштабирования

### 1.2. Типы горячих шардов

1. **Горячие шарды по запросам** - шард получает значительно больше запросов, чем другие
2. **Горячие шарды по данным** - шард содержит значительно больше данных, чем другие
3. **Горячие шарды по операциям записи** - шард получает значительно больше операций записи
4. **Горячие шарды по операциям чтения** - шард получает значительно больше операций чтения

---

## 2. Метрики мониторинга

### 2.1. Метрики уровня шарда

| Метрика | Где собираем | Как собираем | Пороговые значения |
|---------|--------------|--------------|-------------------|
| **Операции чтения в секунду (ops/sec)** | MongoDB shard nodes | `db.serverStatus().opcounters.query` через MongoDB Exporter | **Хорошо:** отклонение < 20% от среднего по всем шардам<br>**Плохо:** отклонение > 50% от среднего<br>**Критично:** отклонение > 100% от среднего |
| **Операции записи в секунду (ops/sec)** | MongoDB shard nodes | `db.serverStatus().opcounters.insert/update/delete` через MongoDB Exporter | **Хорошо:** отклонение < 20% от среднего<br>**Плохо:** отклонение > 50% от среднего<br>**Критично:** отклонение > 100% от среднего |
| **CPU утилизация (%)** | Shard nodes (OS level) | Node Exporter, системные метрики | **Хорошо:** отклонение < 20% от среднего по всем шардам<br>**Плохо:** отклонение > 50% от среднего<br>**Критично:** отклонение > 100% от среднего или абсолютное значение > 85% |
| **Использование памяти (%)** | Shard nodes (OS level) | Node Exporter, `db.serverStatus().mem` | **Хорошо:** отклонение < 20% от среднего<br>**Плохо:** отклонение > 50% от среднего<br>**Критично:** отклонение > 100% от среднего или абсолютное значение > 90% |
| **I/O операций в секунду (IOPS)** | Shard nodes (disk level) | Node Exporter, iostat | **Хорошо:** отклонение < 20% от среднего<br>**Плохо:** отклонение > 50% от среднего<br>**Критично:** отклонение > 100% от среднего или > 95% от максимальных IOPS диска |
| **Размер данных на шарде (GB)** | MongoDB shard nodes | `sh.status()` через скрипты, `db.stats()` | **Хорошо:** отклонение < 30% от среднего<br>**Плохо:** отклонение 30-50%<br>**Критично:** отклонение > 50% |
| **Количество чанков на шарде** | Config servers | `sh.status()` через MongoDB Exporter или скрипты | **Хорошо:** отклонение < 30% от среднего<br>**Плохо:** отклонение 30-50%<br>**Критично:** отклонение > 50% |
| **Процент запросов к шарду от общего числа** | Application logs, MongoDB profiler | Анализ логов приложения, `db.setProfilingLevel()` | **Хорошо:** равномерное распределение (±20%)<br>**Плохо:** один шард > 40% запросов<br>**Критично:** один шард > 60% запросов |

### 2.2. Метрики уровня коллекции

| Метрика | Где собираем | Как собираем | Пороговые значения |
|---------|--------------|--------------|-------------------|
| **Распределение документов по шардам** | Config servers | `db.collection.getShardDistribution()` через скрипты | **Хорошо:** отклонение < 30% от среднего<br>**Плохо:** отклонение 30-50%<br>**Критично:** отклонение > 50% |
| **Распределение операций по категориям (products)** | Application logs, MongoDB profiler | Анализ логов с фильтрацией по `category` | **Хорошо:** ни одна категория < 50% запросов<br>**Плохо:** одна категория 50-70% запросов<br>**Критично:** одна категория > 70% запросов |
| **Распределение операций по customer_id (orders)** | Application logs, MongoDB profiler | Анализ логов с группировкой по `customer_id` | **Хорошо:** топ-10 клиентов < 30% запросов<br>**Плохо:** топ-10 клиентов 30-50% запросов<br>**Критично:** топ-10 клиентов > 50% запросов |

### 2.3. Метрики уровня кластера

| Метрика | Где собираем | Как собираем | Пороговые значения |
|---------|--------------|--------------|-------------------|
| **Коэффициент вариации нагрузки между шардами** | Aggregated from shard metrics | Статистический расчет: std_dev / mean | **Хорошо:** < 0.2<br>**Плохо:** 0.2-0.4<br>**Критично:** > 0.4 |
| **Количество миграций чанков в час** | Config servers | `config.changelog` collection, мониторинг `moveChunk` операций | **Хорошо:** < 10 миграций/час<br>**Плохо:** 10-50 миграций/час<br>**Критично:** > 50 миграций/час (может указывать на нестабильность) |

## 3. Технологический стек для мониторинга

### 3.1. Сбор метрик

#### 3.1.1. MongoDB Exporter (Prometheus)
- **Назначение:** сбор метрик из MongoDB
- **Метрики:** операции чтения/записи, распределение данных, количество чанков
- **Развертывание:** отдельный сервис, опрашивающий MongoDB через API
- **Интервал сбора:** 15-30 секунд

#### 3.1.2. Node Exporter (Prometheus)
- **Назначение:** сбор системных метрик хостов
- **Метрики:** CPU, память, диск, I/O
- **Развертывание:** агент на каждом хосте MongoDB
- **Интервал сбора:** 15 секунд

#### 3.1.3. MongoDB Profiler
- **Назначение:** анализ распределения запросов по категориям и клиентам
- **Метрики:** типы операций, распределение по шард-ключам
- **Настройка:** профилирование уровня 1 (только медленные запросы > 100ms)
- **Хранение:** коллекция `system.profile` с TTL 7 дней

#### 3.1.4. Application Logs Analysis
- **Назначение:** анализ паттернов запросов для выявления горячих ключей
- **Метрики:** распределение запросов по категориям (products), по customer_id (orders)
- **Методы:** агрегация логов приложения по шард-ключам

### 3.2. Хранение и агрегация метрик

#### 3.2.1. Prometheus
- **Назначение:** временное хранение метрик (15-30 дней)
- **Особенности:** эффективное хранение временных рядов, мощный язык запросов PromQL
- **Retention:** 30 дней для детальных метрик, 1 год для агрегированных

#### 3.2.2. Long-term Storage (опционально)
- **Варианты:** VictoriaMetrics, Thanos, Cortex
- **Назначение:** долгосрочное хранение метрик (1+ год)
- **Использование:** исторический анализ, планирование емкости

### 3.3. Визуализация

#### 3.3.1. Grafana
- **Назначение:** дашборды для визуализации метрик дисбаланса
- **Дашборды:**
  - Распределение операций чтения/записи между шардами
  - Распределение CPU, памяти, IOPS между шардами
  - Распределение данных и чанков по шардам
  - Распределение запросов по категориям (products) и клиентам (orders)
  - Коэффициент вариации нагрузки между шардами
  - Тренды дисбаланса

#### 3.3.2. MongoDB Compass 
- **Назначение:** административный интерфейс для ручного анализа
- **Использование:** проверка распределения данных через `db.collection.getShardDistribution()`, анализ `sh.status()`

### 3.4. Алертинг

#### 3.4.1. Alertmanager (Prometheus)
- **Назначение:** управление алертами, дедупликация, группировка, маршрутизация
- **Каналы уведомлений:** Email, Telegram

### 3.5. Автоматизация и реагирование

#### 3.5.1. Скрипт анализа распределения данных
- **Триггер:** алерт о дисбалансе данных (> 50% отклонение размера данных или количества чанков)
- **Действия:**
  - Выполнение `db.collection.getShardDistribution()` для всех коллекций
  - Вычисление коэффициента вариации распределения
  - Генерация отчета с рекомендациями
- **Результат:** отчет в формате JSON/текст, отправка в Telegram/Email

#### 3.5.2. Скрипт анализа горячих ключей
- **Триггер:** алерт о дисбалансе операций (> 50% отклонение операций чтения/записи)
- **Действия:**
  - Анализ логов MongoDB profiler за последний час
  - Группировка запросов по шард-ключам (category для products, customer_id для orders)
  - Выявление топ-N ключей, создающих наибольшую нагрузку
- **Результат:** список горячих ключей с процентом запросов, отправка в Telegram/Email

#### 3.5.3. Ansible Playbook для автоматической перебалансировки
- **Триггер:** дисбаланс данных > 50% и стабилен в течение 1 часа, низкая нагрузка (ночное время)
- **Условия запуска:**
  - Отсутствие активных миграций чанков
  - Низкая нагрузка на кластер (CPU < 50% на всех шардах)
- **Действия:**
  - Проверка статуса балансировщика: `sh.getBalancerState()`
  - Запуск балансировщика: `sh.startBalancer()`
  - Мониторинг процесса миграции через `sh.status()`
  - Остановка балансировщика при обнаружении проблем
- **Ограничения:** не более 10 одновременных миграций, приостановка при росте нагрузки

#### 3.5.4. Скрипт создания тикетов
- **Триггер:** критический дисбаланс категорий (> 70% запросов к одной категории) или критический дисбаланс клиентов (> 50% запросов от топ-10 клиентов)
- **Действия:**
  - Сбор данных о дисбалансе (метрики, анализ горячих ключей)
  - Создание тикета в системе управления задачами (Jira, Redmine и т.д.)
  - Приоритет: High для критических случаев
  - Шаблон тикета включает: описание проблемы, метрики, рекомендации по изменению стратегии шардирования

### 3.6. Логирование

#### 3.6.1. Centralized Logging
- **Варианты:** ELK Stack (Elasticsearch, Logstash, Kibana), Loki, Splunk
- **Назначение:** централизованный сбор и анализ логов приложения
- **Источники:** application logs для анализа распределения запросов по шард-ключам (customer_id, category)
- **Использование:** агрегация логов по шард-ключам и временным интервалам для выявления горячих ключей (см. раздел 3.5.2)

## 4. Стратегии реагирования на проблемы горячих шардов

### 4.1. Уровни критичности и SLA

| Уровень | Характеристики | Время реакции (SLA) | Ответственный |
|---------|----------------|---------------------|---------------|
| **Warning** | Отклонение метрик в зоне "Плохо", без критического влияния на сервис | 8 часов (рабочий день) | Команда DevOps/DB |
| **Critical** | Отклонение метрик в зоне "Критично", заметное влияние на производительность | 1 час | Команда DevOps/DB, при необходимости Team Lead |
| **Incident** | Деградация сервиса, ошибки, недоступность | 15 минут | On-Call Engineer, автоматическая эскалация |

### 4.2. Матрица реагирования

| Триггер | Условие | Кто реагирует | Действия |
|---------|---------|---------------|----------|
| **Дисбаланс операций чтения/записи** | Один шард получает > 50% операций в течение 15 минут | Автоматически | Запуск скрипта анализа распределения данных, уведомление команде |
| **Высокая CPU/память** | Отклонение > 50% от среднего или абсолютное значение > 85% CPU / > 90% памяти в течение 10 минут | Автоматически | Запуск скрипта анализа горячих ключей, уведомление команде |
| **Дисбаланс данных** | Размер данных отклоняется > 50% от среднего | Автоматически | Запуск анализа распределения чанков, рекомендации по перебалансировке |
| **Критический дисбаланс категорий/клиентов** | Одна категория > 70% запросов или топ-10 клиентов > 50% запросов в течение 30 минут | Автоматически | Создание тикета на анализ стратегии шардирования, уведомление команде |
| **Критический дисбаланс** | Один шард > 60% запросов + размер данных отклоняется > 50% | DevOps/DB (Critical) | Ручной анализ, подготовка к перебалансировке или изменению стратегии |
| **Нестабильность миграций** | > 50 миграций/час, ошибки миграций | DevOps/DB (Critical) | Приостановка автоматических миграций, ручной анализ |
| **Дисбаланс после перебалансировки** | Дисбаланс сохраняется или ухудшается | Team Lead / Архитектор | Анализ необходимости изменения стратегии шардирования |
| **Деградация сервиса** | Ошибки > 5% запросов, недоступность | On-Call Engineer (Incident) | Немедленная диагностика, временные меры (rate limiting), корректирующие действия |

### 4.3. Способы устранения горячих шардов

| Способ | Когда применять | Действия |
|--------|-----------------|----------|
| **Перебалансировка чанков** | Дисбаланс данных > 30%, стабилен в течение 1 часа, низкая нагрузка | `db.collection.getShardDistribution()` → `sh.startBalancer()` → мониторинг через `sh.status()` |
| **Изменение стратегии шардирования** | Постоянный дисбаланс из-за неправильного шард-ключа (например, категория "Электроника" > 70% запросов) | Создание новой коллекции с новой стратегией → миграция данных → обновление приложения → удаление старой коллекции |
| **Масштабирование кластера** | Общая нагрузка высока, добавление шардов поможет распределить нагрузку | Добавление новых шардов → автоматическая перебалансировка → мониторинг |
| **Кеширование** | Популярные запросы создают высокую нагрузку на определенные шарды (например, популярные категории товаров) | Внедрение кеширования результатов популярных запросов (Redis, Memcached) на уровне приложения, снижение нагрузки на горячие шарды |
| **Временные меры** | Критический инцидент, требуется быстрое снижение нагрузки | Rate limiting на проблемные категории/клиентов на уровне приложения |

## 2. Общие принципы

| Принцип | Описание |
|---------|----------|
| **Критичность консистентности** | Операции, требующие строгой консистентности (остатки, статусы, активные корзины), всегда используют Primary |
| **Частота обновлений** | Данные, которые часто обновляются, читаются с Primary. Исторические данные и редко изменяемые справочники могут читаться с Secondary |
| **Бизнес-риски** | Операции, где устаревшие данные могут привести к бизнес-проблемам (overselling, неверный статус заказа), используют Primary |
| **Допустимая задержка** | Для операций на Secondary допустима задержка 10-30 секунд (берем с запасом) |
| **Кеширование** | Для операций чтения каталога товаров рекомендуется использовать кеш приложения (Redis, Memcached) для полного снятия нагрузки с БД. Кеш инвалидируется при изменении данных. |

## Задание 10.2. Концептуальная модель данных для Cassandra

### 2.1. Таблица `orders`

```cql
CREATE TABLE orders (
    customer_id TEXT,
    order_date DATE,              -- Только дата для partition key
    order_id UUID,
    order_timestamp TIMESTAMP,    -- Полная дата и время для сортировки
    status TEXT,
    total_amount DECIMAL,
    geo_zone TEXT,
    PRIMARY KEY ((customer_id, order_date), order_timestamp, order_id)
) WITH CLUSTERING ORDER BY (order_timestamp DESC, order_id DESC);
```

**Partition Key:** `(customer_id, order_date)` где `order_date` имеет тип `DATE`
- **Обоснование**: 
  - Все заказы клиента за **день** в одной партиции - локализация запросов
  - `order_date` (только дата, без времени) предотвращает создание тысяч мелких партиций
  - Предотвращает горячие партиции (один клиент с миллионами заказов распределяется по дням)
  - Равномерное распределение по дням, а не по минутам

**Clustering Keys:** `(order_timestamp DESC, order_id DESC)`
- `order_timestamp` - полная дата и время для сортировки внутри партиции
- `order_id` - для уникальности и получения последних заказов первыми

**Важно:** Для запросов за несколько дней нужно делать несколько запросов (по одному на каждый день), т.к. partition key включает дату. Это нормальная практика в Cassandra.

**Таблица для товаров в заказе (нормализация):**
```cql
CREATE TABLE order_items (
    customer_id TEXT,
    order_date DATE,
    order_id UUID,
    item_position INT,            -- Позиция товара в заказе
    product_id UUID,
    product_name TEXT,
    price DECIMAL,
    quantity INT,
    PRIMARY KEY ((customer_id, order_date, order_id), item_position)
) WITH CLUSTERING ORDER BY (item_position ASC);
```

**Таблица для истории статусов (нормализация):**
```cql
CREATE TABLE order_status_history (
    customer_id TEXT,
    order_date DATE,
    order_id UUID,
    changed_at TIMESTAMP,
    status TEXT,
    changed_by TEXT,              -- Опционально: user_id, system, admin_id
    PRIMARY KEY ((customer_id, order_date, order_id), changed_at)
) WITH CLUSTERING ORDER BY (changed_at DESC);
```

**Таблицы для запросов по статусу и геозоне (Query-Based Modeling):**

Вместо вторичных индексов (которые работают медленно на больших объемах) создаются отдельные таблицы для каждого типа запроса:

```cql
-- Таблица для запросов "найти все заказы со статусом X"
CREATE TABLE orders_by_status (
    status TEXT,
    order_date DATE,
    customer_id TEXT,
    order_id UUID,
    order_timestamp TIMESTAMP,
    total_amount DECIMAL,
    geo_zone TEXT,
    PRIMARY KEY ((status, order_date), order_timestamp, order_id)
) WITH CLUSTERING ORDER BY (order_timestamp DESC, order_id DESC);

-- Таблица для запросов "найти все заказы в геозоне X"
CREATE TABLE orders_by_geo_zone (
    geo_zone TEXT,
    order_date DATE,
    customer_id TEXT,
    order_id UUID,
    order_timestamp TIMESTAMP,
    status TEXT,
    total_amount DECIMAL,
    PRIMARY KEY ((geo_zone, order_date), order_timestamp, order_id)
) WITH CLUSTERING ORDER BY (order_timestamp DESC, order_id DESC);
```

**Принцип Query-Based Modeling:**
- Каждая таблица оптимизирована под конкретный тип запроса
- Partition key включает поля, по которым выполняется фильтрация (status, geo_zone)
- При записи заказа данные **дублируются во все необходимые таблицы** (orders, orders_by_status, orders_by_geo_zone)
- Это нормальная практика денормализации в Cassandra - жертвуем дублированием данных ради производительности запросов
- **Важно:** При обновлении статуса заказа нужно обновить записи во всех таблицах (orders и orders_by_status)

**Обоснование нормализации:**
- **Отдельная таблица `order_items`** вместо `LIST<FROZEN<MAP<...>>>`:
  - Позволяет эффективно добавлять/удалять товары без перезаписи всего списка
  - Упрощает запросы к отдельным товарам
  - Избегает проблем с FROZEN (неизменяемые коллекции)
- **Отдельная таблица `order_status_history`** вместо `LIST<FROZEN<MAP<...>>>`:
  - Легко добавлять новые записи в историю
  - Эффективные запросы по времени изменения статуса
  - Сортировка по `changed_at DESC` для получения последних изменений первыми

**Предотвращение горячих партиций:**
- Составной partition key с датой распределяет нагрузку
- При добавлении узлов данные распределяются по token ring без полного перераспределения

### 2.2. Таблица `products`

```cql
CREATE TABLE products (
    category TEXT,
    product_id UUID,
    name TEXT,
    price DECIMAL,
    attributes MAP<TEXT, TEXT>,
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    PRIMARY KEY ((category), product_id)
) WITH CLUSTERING ORDER BY (product_id ASC);
```

**Partition Key:** `category`
- **Обоснование**:
  - Запросы по категориям локализованы в одной партиции
  - Равномерное распределение при большом количестве категорий
  - При росте категории данные распределяются по узлам через token ring

**Clustering Key:** `product_id`
- Уникальная идентификация товара внутри категории

**Назначение таблицы `products`:**
- Хранение **медленно меняющихся данных**: название, описание, цена, атрибуты
- Оптимизирована для операций чтения каталога товаров
- Остатки товаров **не хранятся** в этой таблице (см. `product_stock`)

**Таблица для остатков товаров (основная для операций с остатками):**
```cql
CREATE TABLE product_stock (
    product_id UUID,
    geo_zone TEXT,
    stock COUNTER,
    PRIMARY KEY ((product_id, geo_zone))
);
```

**Назначение таблицы `product_stock`:**
- Хранение **быстро меняющихся данных**: остатки товаров по геозонам
- Оптимизирована для частых операций инкремента/декремента (COUNTER)
- Эффективные обновления остатков при покупках без копирования всей MAP
- Partition key `(product_id, geo_zone)` позволяет эффективно запрашивать остатки конкретного товара в конкретной геозоне

**Обоснование разделения:**
- **products** - медленно меняющиеся данные (название, цена, описание) - редкие обновления
- **product_stock** - быстро меняющиеся данные (остатки) - частые обновления при каждой покупке
- Избегаем проблем с MAP (копирование всей карты при изменении одного значения)
- COUNTER в `product_stock` обеспечивает атомарные операции инкремента/декремента

**Предотвращение горячих партиций:**
- Если одна категория становится слишком популярной, можно использовать составной ключ `(category, bucket)` где `bucket = hash(product_id) % N`
  - **N** - количество бакетов (фиксированное число, обычно 4, 8, 16 или 32)
  - Выбирается заранее в зависимости от ожидаемого размера категории
  - Товары категории распределяются по N партициям вместо одной
  - **Компромисс**: для чтения всех товаров категории нужно делать N запросов (по одному на каждый bucket)
- При добавлении узлов Cassandra автоматически перераспределяет данные по token ring

**Пример использования bucket-подхода:**
```cql
CREATE TABLE products (
    category TEXT,
    bucket INT,              -- bucket = hash(product_id) % 8
    product_id UUID,
    name TEXT,
    price DECIMAL,
    -- ... остальные поля
    PRIMARY KEY ((category, bucket), product_id)
);
-- Для чтения всех товаров категории "electronics" нужно 8 запросов:
-- WHERE category = 'electronics' AND bucket = 0
-- WHERE category = 'electronics' AND bucket = 1
-- ... и т.д. до bucket = 7
```

### 2.3. Таблица `carts`

**Предположение:** У пользователя одна активная корзина. Для гостей используется та же таблица.

```cql
CREATE TABLE carts (
    user_id TEXT,              -- Для авторизованных: реальный ID, для гостей: пустая строка ""
    session_id TEXT,           -- Для гостей: реальный session_id, для авторизованных: может быть null
    status TEXT,               -- "active", "ordered", "abandoned"
    created_at TIMESTAMP,
    updated_at TIMESTAMP,
    PRIMARY KEY ((user_id, session_id))
) WITH default_time_to_live = 2592000; -- 30 дней
```

**Partition Key:** `(user_id, session_id)`
- **Для авторизованных пользователей**: `user_id` = реальный ID пользователя, `session_id` = пустая строка `""`
- **Для гостей**: `user_id` = пустая строка `""`, `session_id` = реальный session_id
- **Обоснование**:
  - Одна активная корзина на пользователя/сессию (уникальность обеспечивается составным ключом)
  - Быстрый доступ к корзине по составному ключу
  - Равномерное распределение по пользователям и сессиям
  - Единая таблица для авторизованных и гостевых корзин упрощает логику приложения

**Таблица для товаров в корзине (нормализация):**
```cql
CREATE TABLE cart_items (
    user_id TEXT,
    session_id TEXT,
    product_id UUID,
    quantity INT,
    added_at TIMESTAMP,
    PRIMARY KEY ((user_id, session_id), product_id)
) WITH default_time_to_live = 2592000; -- 30 дней
```

**Обоснование нормализации:**
- **Отдельная таблица `cart_items`** вместо `LIST<FROZEN<MAP<...>>>`:
  - Позволяет эффективно добавлять/удалять товары без перезаписи всего списка
  - Упрощает запросы к отдельным товарам
  - Избегает проблем с FROZEN (неизменяемые коллекции)
  - Эффективные обновления количества товара

**Предотвращение горячих партиций:**
- Равномерное распределение по user_id/session_id
- TTL автоматически очищает старые корзины
- Одна корзина на партицию (нет множественных корзин одного пользователя)

## Задание 10.3. Стратегии обеспечения целостности данных

### 3.1. Hinted Handoff

**Применение:**
- ✅ **orders** - при недоступности узла-реплики hint сохраняется и доставляется после восстановления
- ✅ **products** - обновления остатков критичны, hints обеспечивают доставку после восстановления
- ✅ **carts** - изменения корзины не должны теряться

**Настройка:**
```cql
-- В cassandra.yaml
hinted_handoff_enabled: true
max_hint_window_in_ms: 10800000  -- 3 часа
```

**Компромисс:** 
- ✅ Низкая latency записи (не ждём восстановления узла)
- ⚠️ Риск потери данных при длительном простое узла (> max_hint_window)

### 3.2. Read Repair

**Применение:**
- ✅ **orders** - чтение истории заказов (LOCAL_QUORUM reads) с автоматическим исправлением расхождений
- ✅ **products** - чтение остатков (LOCAL_QUORUM) и каталога (LOCAL_ONE) для исправления расхождений
- ⚠️ **carts** - только для некритичных операций (чтение старых корзин с LOCAL_ONE)

**Настройка:**
```cql
-- Примеры запросов с разными consistency levels

-- Чтение истории заказов (LOCAL_QUORUM для баланса производительности и консистентности)
SELECT * FROM orders WHERE customer_id = ? AND order_date = ? 
  USING CONSISTENCY LOCAL_QUORUM;

-- Чтение остатков товара (LOCAL_QUORUM для предотвращения overselling)
SELECT * FROM product_stock WHERE product_id = ? AND geo_zone = ?
  USING CONSISTENCY LOCAL_QUORUM;

-- Чтение каталога товаров (LOCAL_ONE для низкой latency)
SELECT * FROM products WHERE category = ?
  USING CONSISTENCY LOCAL_ONE;

-- Финальное подтверждение заказа (QUORUM для критически важной операции)
UPDATE orders SET status = 'confirmed' WHERE customer_id = ? AND order_date = ? AND order_id = ?
  USING CONSISTENCY QUORUM;

-- В cassandra.yaml
read_request_timeout_in_ms: 5000
```

**Компромисс:**
- ✅ Автоматическое исправление расхождений при чтении
- ⚠️ Увеличение latency при обнаружении расхождений (дополнительные запросы к репликам)

### 3.3. Anti-Entropy Repair

**Применение:**
- ✅ **orders** - регулярный repair для критичных данных (ежедневно)
- ✅ **products** - регулярный repair для остатков (каждые 6 часов)
- ✅ **carts** - менее частый repair (еженедельно), т.к. данные временные

**Компромисс:**
- ✅ Гарантированное обнаружение и исправление всех расхождений
- ⚠️ Высокая нагрузка на кластер во время repair (рекомендуется в off-peak время)

### 3.4. Матрица выбора стратегий

| Сущность | Операция | Hinted Handoff | Read Repair | Anti-Entropy Repair | Consistency Level (Write/Read) |
|----------|----------|----------------|-------------|---------------------|-------------------------------|
| **orders** | Создание заказа | ✅ Да | ✅ Да | ✅ Да (ежедневно) | LOCAL_QUORUM / - |
| **orders** | Финальное подтверждение заказа | ✅ Да | ✅ Да | ✅ Да (ежедневно) | QUORUM / - |
| **orders** | Чтение истории заказов | ✅ Да | ✅ Да (LOCAL_QUORUM) | ✅ Да (ежедневно) | - / LOCAL_QUORUM |
| **products** | Обновление остатков | ✅ Да | ✅ Да | ✅ Да (каждые 6ч) | LOCAL_QUORUM / - |
| **products** | Чтение остатков | ✅ Да | ✅ Да (LOCAL_QUORUM) | ✅ Да (каждые 6ч) | - / LOCAL_QUORUM |
| **products** | Чтение каталога (название, цена) | ✅ Да | ✅ Да (LOCAL_ONE) | ✅ Да (каждые 6ч) | - / LOCAL_ONE |
| **carts** | Обновление активной корзины | ✅ Да | ⚠️ Ограниченно | ⚠️ Еженедельно | LOCAL_QUORUM / LOCAL_QUORUM |
| **carts** | Чтение старых корзин | ✅ Да | ⚠️ Ограниченно | ⚠️ Еженедельно | - / LOCAL_ONE |

### 3.5. Обоснование выбора

**orders:**
- **LOCAL_QUORUM для создания заказа** - баланс между консистентностью и производительностью в пределах дата-центра
- **QUORUM для финального подтверждения заказа** - критически важная операция, требует строгой консистентности
- **LOCAL_QUORUM для чтения истории** - хороший баланс, Read Repair исправляет расхождения
- **Read Repair** - автоматическое исправление при чтении истории
- **Anti-Entropy Repair** - ежедневный repair для гарантии целостности
- **Hinted Handoff** - обеспечение доставки при временных сбоях

**products:**
- **LOCAL_QUORUM для остатков (write/read)** - предотвращение overselling с хорошей производительностью в пределах дата-центра
- **LOCAL_ONE для чтения каталога** - низкая latency, допустима eventual consistency для медленно меняющихся данных (название, цена, описание)
- **Read Repair** - исправление расхождений в описаниях при чтении с LOCAL_ONE
- **Anti-Entropy Repair каждые 6 часов** - баланс между целостностью и нагрузкой

**carts:**
- **LOCAL_QUORUM для активных корзин** - критичность при оформлении заказа, но без излишней latency QUORUM
- **LOCAL_ONE для старых корзин** - допустима eventual consistency для неактивных данных
- **Менее частый Anti-Entropy Repair** - данные временные, TTL очищает старые записи

## Резюме

**Преимущества миграции на Cassandra:**
1. ✅ Быстрое горизонтальное масштабирование без полного перераспределения данных
2. ✅ Leaderless-репликация обеспечивает высокую отказоустойчивость
3. ✅ Равномерное распределение данных через token ring
4. ✅ Оптимизация для высоконагруженных операций записи

**Компромиссы:**
1. ⚠️ Eventual consistency требует правильного выбора consistency levels
2. ⚠️ Необходимость регулярного Anti-Entropy Repair для гарантии целостности
3. ⚠️ Изменение модели данных (что, порой, вызывает необходимость нескольких запросов для чтения одной сущности)
